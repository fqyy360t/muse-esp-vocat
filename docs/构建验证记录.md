### 3.2 两处容易误判的 Kconfig 提示（都不是缺陷）

1. `CONFIG_ESPTOOLPY_FLASHMODE="dout"` 看似与 OPI 矛盾。查 IDF `esptool_py/Kconfig.projbuild:79-90`：
   OPI 时该字符串默认就是 `dout`，注释原文说明「一/二级 bootloader 不支持 OPI，ROM 从 eFuse
   读取 flash 模式，不用管这个 dout 选项」。**保持原样**。
2. overlay 第 41 行 `CONFIG_SPIRAM_ALLOW_STACK_EXTERNAL_MEMORY` 被 IDF 提示
   `was replaced with CONFIG_FREERTOS_TASK_CREATE_ALLOW_EXT_MEM`。查上游：
   `devices/AGENTS.md:261` **明确要求**写旧符号，且 20+ 份板 overlay 全部这么写。
   这是 IDF 的兼容迁移，**不要擅自改成新符号**，否则偏离 SDK 规范（v6.0.3 下行为由 IDF 决定）。
3. 大量 `unknown kconfig symbol LV_*` 警告来自 v5.5.5 与 SDK 期望的 v6.0.3 组件版本差异，
   属跨版本使用，不是本适配包引入。
4. `No SDK token: set CONFIG_GADGET_SDK_TOKEN` 是配对功能提示，不影响编译；上板配对前需配置。

CI 容器里跑。另：全量 discover 会触发本机安全策略（某测试尝试启动被黑名单拦下的程序），
本轮不重试、不绕过。

## 5. 完整 `build` —— 板文件编译通过，全量链接被上游版本门槛挡住

**过程**：首次 `idf.py build` 在 bootloader 生成后停滞（905 个 `.obj` 落盘、3 个
`xtensa-esp32s3-elf-gcc` 僵死 16 分钟且 CPU≈0、60 秒内零产物更新）。判定为 Windows 上
编译进程僵死，终止后以 `CCACHE_DISABLE=1` + `ninja -j 2` 增量重跑（输出重定向到文件，
避免管道阻塞），推进到 **1277/1355、零编译错误** 后再次出现同类僵死。

**改走单目标验证**（本轮最关键的一步）：

```
ninja -C build-muse-esp-vocat -j 1 \
  esp-idf/muse/CMakeFiles/__idf_muse.dir/boards/board_esp_vocat.c.obj
→ exit code 0，产出 board_esp_vocat.c.obj（126 KB）
```

ninja 同时补齐了依赖链上的 `lvgl__lvgl`、`esp_lv_decoder`、`esp_lv_fs`、
`esp_lvgl_adapter` 静态库。**结论：新增板级 C 代码在 ESP-IDF v5.5.5 下编译通过，
无语法错误、无头文件缺失、无 API 不兼容。**

**再用 `ninja -j 1` 续跑全量**，在 `[57/74]` 处拿到明确的失败原因：

```
FAILED: esp-idf/main/CMakeFiles/__idf_main.dir/link_pairing.c.obj
.../main/link_pairing.c:31:10: fatal error: mbedtls/private/gcm.h: No such file or directory
ninja: build stopped: subcommand failed.
```

归因核实（三条证据）：

| 证据 | 结果 |
|---|---|
| 未打补丁的原始 SDK `main/link_pairing.c:31` | **同样**有 `#include "mbedtls/private/gcm.h"` → 不是适配包引入 |
| 本机 IDF v5.5.5 的 mbedtls | 只有 `mbedtls/gcm.h`、`port/include/mbedtls/gcm.h`，**没有 `mbedtls/private/`** |
| SDK 自身约束 | README/CI/`board.sh` 都要求 **v6.0.3**（"Other versions aren't supported"） |

=> 这是**跨版本不兼容**，发生在上游共享层 `main/`，与 `components/muse/boards/` 无关。
按既定原则**不为迁就 v5.5.5 去改共享层代码**，因此本机不产出 `muse-gadget.bin`。
两次「卡住」也都是编译进程僵死，不是代码错误——单线程跑到 57/74 才暴露真实报错。
