### 3.2 两处容易误判的 Kconfig 提示（都不是缺陷）

1. `CONFIG_ESPTOOLPY_FLASHMODE="dout"` 看似与 OPI 矛盾。查 IDF `esptool_py/Kconfig.projbuild:79-90`：
   OPI 时该字符串默认就是 `dout`，注释原文说明「一/二级 bootloader 不支持 OPI，ROM 从 eFuse
   读取 flash 模式，不用管这个 dout 选项」。**保持原样**。
2. overlay 第 41 行 `CONFIG_SPIRAM_ALLOW_STACK_EXTERNAL_MEMORY` 被 IDF 提示
   `was replaced with CONFIG_FREERTOS_TASK_CREATE_ALLOW_EXT_MEM`。查上游：
   `devices/AGENTS.md:261` **明确要求**写旧符号，且 20+ 份板 overlay 全部这么写。
   这是 IDF 的兼容迁移，**不要擅自改成新符号**，否则偏离 SDK 规范（v6.0.3 下行为由 IDF 决定）。
3. 大量 `unknown kconfig symbol LV_*` 警告来自 v5.5.5 与 SDK 期望的 v6.0.3 组件版本差异，
   属跨版本使用，不是本适配包引入。
4. `No SDK token: set CONFIG_GADGET_SDK_TOKEN` 是配对功能提示，不影响编译；上板配对前需配置。

## 5. 完整 `build` —— 板文件编译通过，全量链接被上游版本门槛挡住

**过程**：首次 `idf.py build` 在 bootloader 生成后停滞（905 个 `.obj` 落盘、3 个
`xtensa-esp32s3-elf-gcc` 僵死 16 分钟且 CPU≈0、60 秒内零产物更新）。判定为 Windows 上
编译进程僵死，终止后以 `CCACHE_DISABLE=1` + `ninja -j 2` 增量重跑（输出重定向到文件，
避免管道阻塞），推进到 **1277/1355、零编译错误** 后再次出现同类僵死。

**改走单目标验证**（本轮最关键的一步）：

```
ninja -C build-muse-esp-vocat -j 1 \
  esp-idf/muse/CMakeFiles/__idf_muse.dir/boards/board_esp_vocat.c.obj
→ exit code 0，产出 board_esp_vocat.c.obj（126 KB）
```

ninja 同时补齐了依赖链上的 `lvgl__lvgl`、`esp_lv_decoder`、`esp_lv_fs`、
`esp_lvgl_adapter` 静态库。**结论：新增板级 C 代码在 ESP-IDF v5.5.5 下编译通过，
无语法错误、无头文件缺失、无 API 不兼容。**

**再用 `ninja -j 1` 续跑全量**，在 `[57/74]` 处拿到明确的失败原因：

```
FAILED: esp-idf/main/CMakeFiles/__idf_main.dir/link_pairing.c.obj
.../main/link_pairing.c:31:10: fatal error: mbedtls/private/gcm.h: No such file or directory
ninja: build stopped: subcommand failed.
```

归因核实（三条证据）：

| 证据 | 结果 |
|---|---|
| 未打补丁的原始 SDK `main/link_pairing.c:31` | **同样**有 `#include "mbedtls/private/gcm.h"` → 不是适配包引入 |
| 本机 IDF v5.5.5 的 mbedtls | 只有 `mbedtls/gcm.h`、`port/include/mbedtls/gcm.h`，**没有 `mbedtls/private/`** |
| SDK 自身约束 | README/CI/`board.sh` 都要求 **v6.0.3**（"Other versions aren't supported"） |

=> 这是**跨版本不兼容**，发生在上游共享层 `main/`，与 `components/muse/boards/` 无关。
按既定原则**不为迁就 v5.5.5 去改共享层代码**，因此本机不产出 `muse-gadget.bin`。
两次「卡住」也都是编译进程僵死，不是代码错误——单线程跑到 57/74 才暴露真实报错。

## 7. ESP-IDF v6.0.3 容器编译 —— 全量链接成功，两块板均通过（2026-11-06 22:54）

**镜像**：`docker.io/espressif/idf:v6.0.3`，digest `sha256:54278f2c01e6...`，解压后 **15.6 GB**，
8 层（压缩 5.14 GiB，最大层 3.6 GB）。`IDF_PATH=/opt/esp/idf`，Python venv `idf6.0_py3.12_env`。

**调用方式**：镜像 entrypoint `/opt/esp/entrypoint.sh` 会 `source $IDF_PATH/export.sh` 再 `exec "$@"`。
直接用 `--entrypoint sh` 调 `idf.py` 会报 `No module named 'rich_click'`——必须走默认 entrypoint，
或自己先 `source export.sh`。

**构建策略**（脚本 `.verify/build_in_container.sh`）：
把 `/host/esp32` 用 `tar --exclude='./build*'` 复制到容器内 `/work`（overlayfs），
避开 Windows 挂载盘的编译性能坑；新建 `build-linux-vocat`，不复用 Windows/v5.5.5 的 CMake 缓存；
产物 `cp` 回 `/host/out`。`IDF_CCACHE_ENABLE=0`，并对 `idf.py` 加 `timeout 2400` 防止无限挂起。

### 7.1 三次失败与根因

| 尝试 | 现象 | 归因 |
|---|---|---|
| 1. 带代理 `host.docker.internal:12334` | `CMake Error: Cannot establish a connection to the component registry`，URL `components-file.espressif.com/.../cjson.json` | 不是网络不通：容器内**直连**与经代理访问 `components.espressif.com` / `components-file...` / `api.github.com` 全部 **HTTP 200**；IDF venv Python 的 `requests` 同样 200。带代理的对照 `reconfigure` 也能跑，故不能把失败归咎于代理本身，属组件仓库偶发连接抖动 |
| 2. 去掉代理直接 build | 卡在 `NOTE: [19/20] lvgl/lvgl` 之后 12 分钟，`prepare_components` 进程 CPU 0.4%、日志 1.5 分钟不动 | 组件管理器联网核对第 20 个依赖时挂起（无整体超时）。**根因**：源码里的 `dependencies.lock` 是 v5.5.5 时代的 `version: 2.0.0 / idf 5.5.5`，v6.0.3 管理器是 3.0.0 → 重建 lock + `Direct dependencies have changed, solving dependencies` → 联网解析 20 个依赖 |
| 3. 禁用组件管理器离线编译 | ① `IDF_COMPONENT_MANAGER=0` + 复制 `managed_components` 到 `components/` → `Failed to resolve component 'esp_mmap_assets'`（组件管理器负责把 `espressif__xxx` 映射成短名）；② 目录去前缀改名 → `esp_lvgl_adapter/CMakeLists.txt:43 idf_component_get_property` 报参数错误 | 这些组件深度依赖组件管理器注入的 CMake 属性，**不能禁用**。此路放弃 |

**最终解法（不绕过、不降级共享层）**：先用 v6.0.3 单独跑一次 `reconfigure` 生成新版
`dependencies.lock`（`version: 3.0.0`、`idf 6.0.3`、`manifest_hash` 不变），把它回写源码；
之后 build 时组件管理器不再重新解析下载。**这是版本升级时最干净的做法**：
让新版工具链自己重写自己的锁文件，而不是手工改格式或禁用它。
