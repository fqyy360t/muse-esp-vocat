### 3.2 两处容易误判的 Kconfig 提示（都不是缺陷）

1. `CONFIG_ESPTOOLPY_FLASHMODE="dout"` 看似与 OPI 矛盾。查 IDF `esptool_py/Kconfig.projbuild:79-90`：

2. overlay 第 41 行 `CONFIG_SPIRAM_ALLOW_STACK_EXTERNAL_MEMORY` 被 IDF 提示
   `was replaced with CONFIG_FREERTOS_TASK_CREATE_ALLOW_EXT_MEM`。查上游：
   `devices/AGENTS.md:261` **明确要求**写旧符号，且 20+ 份板 overlay 全部这么写。

3. 大量 `unknown kconfig symbol LV_*` 警告来自 v5.5.5 与 SDK 期望的 v6.0.3 组件版本差异，

4. `No SDK token: set CONFIG_GADGET_SDK_TOKEN` 是配对功能提示，不影响编译；上板配对前需配置。

## 7. ESP-IDF v6.0.3 容器编译 —— 全量链接成功，两块板均通过（2026-11-06 22:54）

**镜像**：`docker.io/espressif/idf:v6.0.3`，digest `sha256:54278f2c01e6...`，解压后 **15.6 GB**，
8 层（压缩 5.14 GiB，最大层 3.6 GB）。`IDF_PATH=/opt/esp/idf`，Python venv `idf6.0_py3.12_env`。

**调用方式**：镜像 entrypoint `/opt/esp/entrypoint.sh` 会 `source $IDF_PATH/export.sh` 再 `exec "$@"`。
直接用 `--entrypoint sh` 调 `idf.py` 会报 `No module named 'rich_click'`——必须走默认 entrypoint，
或自己先 `source export.sh`。

**构建策略**（脚本 `.verify/build_in_container.sh`）：
把 `/host/esp32` 用 `tar --exclude='./build*'` 复制到容器内 `/work`（overlayfs），
避开 Windows 挂载盘的编译性能坑；新建 `build-linux-vocat`，不复用 Windows/v5.5.5 的 CMake 缓存；
产物 `cp` 回 `/host/out`。`IDF_CCACHE_ENABLE=0`，并对 `idf.py` 加 `timeout 2400` 防止无限挂起。

### 7.1 三次失败与根因

| 尝试 | 现象 | 归因 |
|---|---|---|
| 1. 带代理 `host.docker.internal:12334` | `CMake Error: Cannot establish a connection to the component registry`，URL `components-file.espressif.com/.../cjson.json` | 不是网络不通：容器内**直连**与经代理访问 `components.espressif.com` / `components-file...` / `api.github.com` 全部 **HTTP 200**；IDF venv Python 的 `requests` 同样 200。带代理的对照 `reconfigure` 也能跑，故不能把失败归咎于代理本身，属组件仓库偶发连接抖动 |
| 2. 去掉代理直接 build | 卡在 `NOTE: [19/20] lvgl/lvgl` 之后 12 分钟，`prepare_components` 进程 CPU 0.4%、日志 1.5 分钟不动 | 组件管理器联网核对第 20 个依赖时挂起（无整体超时）。**根因**：源码里的 `dependencies.lock` 是 v5.5.5 时代的 `version: 2.0.0 / idf 5.5.5`，v6.0.3 管理器是 3.0.0 → 重建 lock + `Direct dependencies have changed, solving dependencies` → 联网解析 20 个依赖 |
| 3. 禁用组件管理器离线编译 | ① `IDF_COMPONENT_MANAGER=0` + 复制 `managed_components` 到 `components/` → `Failed to resolve component 'esp_mmap_assets'`（组件管理器负责把 `espressif__xxx` 映射成短名）；② 目录去前缀改名 → `esp_lvgl_adapter/CMakeLists.txt:43 idf_component_get_property` 报参数错误 | 这些组件深度依赖组件管理器注入的 CMake 属性，**不能禁用**。此路放弃 |

**最终解法（不绕过、不降级共享层）**：先用 v6.0.3 单独跑一次 `reconfigure` 生成新版
`dependencies.lock`（`version: 3.0.0`、`idf 6.0.3`、`manifest_hash` 不变），把它回写源码；
之后 build 时组件管理器不再重新解析下载。**这是版本升级时最干净的做法**：
让新版工具链自己重写自己的锁文件，而不是手工改格式或禁用它。

## 8. 实物烧录 COM27 + 启动日志验证（2026-11-06 23:05）

### 8.1 为什么用宿主机 esptool

容器（Linux）无法访问 Windows 的 `COM27`，所以**编译在容器、烧录在宿主机**。
烧录工具用本机 IDF 5.5.5 的 python env 自带的 `esptool 4.12.0`
（`/c/Espressif/python_env/idf5.5_py3.11_env/Scripts/python.exe`），
与编译用的 IDF 6.0.3 版本不同但完全兼容。

只读探测 `flash_id`：

```
Chip is ESP32-S3 (QFN56) (revision v0.2)
Features: WiFi, BLE, Embedded PSRAM 16MB (AP_1v8)
USB mode: USB-Serial/JTAG      MAC: XX:XX:XX:XX:XX:XX
Manufacturer: c2   Device: 8039   Detected flash size: 32MB
Flash type set in eFuse: octal (8 data lines)
```

与 `docs/esp-vocat-硬件接口定义.md` 的实物实测一致。

### 8.2 烧录参数来源与产物

不用早期 v5.5.5 的 `flash_args`，直接从构建容器取权威文件：

```
docker cp vocat-v603:/work/build-linux-vocat/flasher_args.json  .verify/out/
docker cp vocat-v603:/work/build-linux-vocat/{flash_args,ota_data_initial.bin} .verify/out/
docker cp vocat-v603:/work/build-linux-vocat/bootloader/bootloader.bin          .verify/out/bootloader.bin
docker cp vocat-v603:/work/build-linux-vocat/partition_table/partition-table.bin .verify/out/partition-table.bin
docker cp vocat-v603:/work/build-linux-vocat/muse-gadget.bin                    .verify/out/muse-gadget.bin
```

| 地址 | 文件 | SHA256（前 16 位） | 大小 |
|---|---|---|---|
| `0x0` | `bootloader.bin` | `b043a3069b2d627c0` | 21 KB |
| `0x10000` | `partition-table.bin` | `ffa95286aed5ff57` | 3 KB |
| `0x1d000` | `ota_data_initial.bin` | `7d2c7ac4888bfd75c` | 8 KB |
| `0x20000` | `muse-gadget.bin` | `3a1837cef50e22f68` | 2.1 MB |

**第 4 个文件不能省**：`otadata`（`partitions_muse.csv` 的 0x1D000）若残留原厂有效数据，
bootloader 可能选到空的 `ota_1`。分区表在 0x10000、app 在 0x20000，是本项目双 OTA 布局，
别套通用的 0x8000 / 0x10000。

烧录命令（`flasher_args.json` 原样翻译，`--after hard_reset`）：

```bash
python -m esptool --chip esp32s3 --port COM27 --baud 921600 \
  --before default_reset --after hard_reset write_flash \
  --flash_mode dout --flash_size keep --flash_freq 80m \
  0x0 bootloader.bin 0x10000 partition-table.bin \
  0x1d000 ota_data_initial.bin 0x20000 muse-gadget.bin
```

> `--flash_mode dout` 看着和 `CONFIG_ESPTOOLPY_FLASHMODE_OPI=y` 冲突，其实是 IDF 对
> Octal Flash 的标准组合：esptool 以 DOUT 写入，运行时 bootloader 依 `OCT_FLASH` 切 OPI。
> `--flash_size keep` 保留镜像头 16 MB，不去匹配物理 32 MB。

**结果**：`FLASH_RC=0`；4 段全部 `Hash of data verified`；app 段 2166784 字节

## 9. 仓库形态与 `setup.py` 一键准备验证（2026-11-06 23:40）

**决策**：仓库名定为 `muse-esp-vocat`，形态选「轻量适配包 + 一键脚本」——
**不把上游 SDK 源码带进仓库**。事实对比：

| | 本仓库 | 上游 `esp32/` | `.verify/esp32`（本地验证副本） |
|---|---|---|---|
| 文件数 | 13 → 16 | 948 | 8165 |
| 体积 | 214 KB → 约 220 KB | 28 MB（整仓 43 MB） | 528 MB（含编译产物） |
| 入库 | 是 | 否 | 否，`.gitignore` 排除 |

理由：上游 Apache-2.0（面板表另源自 MIT 的 `78/xiaozhi-esp32`），整包复制带来许可证责任
与合并负担；overlay 只带新增文件 + 19 处锚点补丁，能对任意 SDK 副本生效。
代价是 clone 后不能直接编译，故补 `setup.py` / `setup.sh` 与醒目的 README 说明。

**`setup.py` 做的事**：把上游钉在 `463bd2a05380fea4211b0099ad0f70933c108b20`，
clone 到 `vendor/muse-gadget-sdk`（gitignore）→ `checkout --detach` →
`apply.py --check` → `apply.py`。支持 `--sdk-dir`（已有副本）、`--check-only`、
`--mirror`（自定义镜像）。

| 验证项 | 结果 |
|---|---|
| `python setup.py --help` | 参数正常 |
| `python setup.py --sdk-dir F:/git/muse-gadget-sdk --check-only` | `RC=0`，19/0/0/0，未改动上游 |
| **`python setup.py`（真实一键流程）** | **`SETUP_RC=0`**：clone 成功、checkout 到 `463bd2a`、`--check` 19/19、应用 **19/19** |
| 第二次 `python setup.py` | `RC=0`，**0/19/0/0**（全 skip，幂等），复用已有 vendor |
| `sh setup.sh --check-only` | `RC=0`，19 项全 skip |
| `git check-ignore -v vendor/muse-gadget-sdk` | `.gitignore:34:vendor/` 命中，不入库 |

**网络坑**：首次 `git clone` 报 `RPC failed; curl 56 schannel: server closed abruptly
(missing close_notify)` + `early EOF`（Windows 代理 + HTTP/2）。修复：clone 加
`-c http.version=HTTP/1.1`（官方 URL 随即成功），并内置 `gh-proxy.com` 镜像自动回退 +
失败残留目录清理（只清 `<repo>/vendor/` 下）。日志见 `.verify/out/setup.log`。

### 10.2 合并镜像的字节级校验

```
esptool.py --chip esp32s3 merge_bin -o merged.bin \
  --flash_mode keep --flash_freq keep --flash_size keep \
  0x0 bootloader.bin 0x10000 partition-table.bin \
  0x1d000 ota_data_initial.bin 0x20000 muse-gadget.bin
```

输出 `0x231000` 字节。四段与源 bin **逐字节相同**（21360 / 3072 / 8192 / 2166784 B），
三处空隙全为 `0xFF`。用 `keep` 是为了不让 `merge_bin` 改写 bootloader 头部，
保证合并结果与 8.2 节实测的四文件烧录完全一致。
**该单文件方式未单独实烧验证**，已验证路径仍是四文件烧录。
