     合并镜像是「便捷路径」，**未实烧就要如实标注**，已验证路径仍是四文件烧录。
  3. **公开发布前要扫全部入库文件，不只是 Release 附件**：本次在

     2 处真实 BLE 广播名、1 处 PnP InstanceId —— 都是早期写日志时顺手抄进去的。
     教训：**验证记录写进文档那一刻就该脱敏**，不要等到发布前才补。
  4. **脱敏要保字节**：日志含 NUL 与控制字节，用 `latin-1` 往返（1:1 映射）
     做正则替换，UTF-8 decode + replace 会悄悄改掉非法字节、破坏证据完整性。
     二进制产物（含 21 MB ELF）也要逐字节搜 MAC / 凭据 / 本机路径。
  5. **Windows 代理分工**：`git push` 用全局 `http.proxy=127.0.0.1:12334`；
     `gh` CLI 读的是环境变量 `HTTPS_PROXY`（默认被注入 55857），
     需显式给 `HTTPS_PROXY=http://127.0.0.1:12334` 才稳。**不要清空全局代理**，
     清空后会回落到连不上 github 的注入代理。
  6. **Release notes 用文件不用命令行**：`gh release create --notes-file` 走 UTF-8 文件，
     避免 Git Bash 把中文长文本当参数时的编码问题。

- **教育内容(下一棒直接学会)**：
  1. **overlay 与 fork 的取舍**：整包复制上游 Apache-2.0 代码（面板表另源自
     `78/xiaozhi-esp32` 的 MIT）会把别人的许可证责任搬进自己的仓库，且上游更新要手动合并；
     overlay 只带新增文件 + 锚点补丁，代价是 clone 后不能直接编译，必须先准备 SDK 副本。
  2. **overlay 模式的生命线是「固定上游 commit + 锚点自检」**：`setup.py` 把上游钉在
     `463bd2a0`，打补丁前强制跑 `apply.py --check`；上游改了被补丁的文件，
     `--check-only` 会提前报失配，不会静默打坏。
  3. **Windows 代理下 git clone 的坑**：第一次 `git clone` 报
     `RPC failed; curl 56 schannel: server closed abruptly (missing close_notify)` +
     `early EOF`，是 HTTP/2 + schannel 代理的组合问题。加
     `git -c http.version=HTTP/1.1 clone` 后**官方 URL 直接成功**；
     再加一层 `gh-proxy.com` 镜像自动回退做兜底，并在失败时清理残留目录。
  4. **清理残留必须圈定范围**：`cleanup_vendor()` 只在 `dest.parent == ROOT/vendor`
     时才 `rmtree`，绝不误删用户在别处的目录。
  5. **脚本输出只用 ASCII + `sys.stdout.reconfigure`**：中文 Windows 的 GBK 代码页下，
     一旦输出被重定向/管道，含中文或 emoji 的 print 会 `UnicodeEncodeError`。
  6. **验证不能停在 `--help`**：要跑「真实一键流程 + 二次运行幂等 + wrapper +
     `git check-ignore`」四步才算交付。

- **产出(路径)**：`setup.py`（主逻辑，跨平台）/ `setup.sh`（Git Bash 薄封装）/
  `.gitignore` 新增 `vendor/` / `README.md` 说明块与快速开始 /

- **教育内容(下一棒直接学会)**：
  1. **容器负责编译，宿主机负责烧录**：Linux 容器访问不到 Windows 的 `COM27`，
     所以不要试图在容器里跑 `idf.py flash`。烧录用宿主机 esptool 即可，
     **esptool 版本不必与编译用的 IDF 版本一致**（这里 5.5.5 自带的 4.12.0 烧 6.0.3 产物，正常）。
  2. **烧录参数必须取自该次构建的 `flasher_args.json`**，不要拿更早的 v5.5.5
     `flash_args` 想当然。本项目分区表在 **0x10000**（不是常见的 0x8000）、
     app 在 **0x20000**（双 OTA 布局），还有第 4 个文件 `ota_data_initial.bin` 在 0x1d000。
     **otadata 必须一起烧**：原厂固件在同位置可能留过有效 otadata，
     不覆盖就可能让 bootloader 去选空的 `ota_1` 而起不来。
  3. **`--flash_mode dout` 与 `FLASHMODE_OPI=y` 不矛盾**：这是 IDF 对 Octal Flash 的标准做法——
     esptool 用 DOUT 与 flash 通信完成写入，运行时由 bootloader 依 `OCT_FLASH` 切到 OPI。
     别自作主张改成 `opi`。最终判据看串口：`detected chip: mxic (opi)` + `flash io: opi_str`。
  4. **`--flash_size keep` 是刻意的**：保留镜像头里的 16 MB，不去匹配物理 32 MB，
     所以日志里 `Detected size(32768k) larger than ... (16384k)` 是**预期告警**不是故障。
  5. **"Hash verified" 只证明写对了，不证明跑得起来**：必须再抓一次启动日志。
     本次抓日志晚于复位约 0.5 s，错过了 bootloader 头部几行（故看不到
     `Octal Flash Mode Enabled`），但应用侧的 OPI/PSRAM/板级证据足够充分。

     都只是驱动初始化成功；**花屏、颜色反转、触摸对齐、外放可听、唤醒词、电量读数、
     BOOT 键、配对**这些仍需肉眼与交互。别把日志绿灯写成 18 条全过。

## 2026-11-06 · 第六棒：ESP-IDF v6.0.3 容器全量编译 + 双板回归通过 · WorkBuddy

- **做了什么(总结)**：用户自行拉下 `docker.io/espressif/idf:v6.0.3`（15.6 GB 解压）。

  分区余量 48%，`sdkconfig` 逐项确认 Octal Flash / OPI / Oct PSRAM / `MUSE_BOARD_ID`。

- **教育内容(下一棒直接学会)**：
  1. **lock 文件有版本，跨大版本升级会强制重新解析依赖**：源码里的 `dependencies.lock`
     是 v5.5.5 的 `version: 2.0.0 / idf 5.5.5`，v6.0.3 组件管理器是 3.0.0，
     于是 `Recreating lock file` → `Direct dependencies have changed, solving dependencies`
     → 联网解析 20 个依赖 → 偶发挂起。**最干净的解法：先用新版 IDF 单独跑一次
     `reconfigure` 让它自己重写 lock，再回写源码**，不要手工改格式、不要禁用组件管理器。
     新 lock 的差异只有 `version: 3.0.0` 和 `idf 6.0.3`，`manifest_hash` 不变。
  2. **归因要做对照实验，别急着甩锅给代理**：第一次带 `host.docker.internal:12334`
     报 "Cannot establish a connection to the component registry"，我一度判断是代理干扰；
     随后实测容器内**直连** `components.espressif.com` / `components-file...` / `api.github.com`
     全部 HTTP 200，带代理的对照 `reconfigure` 也能跑 → 结论修正为**组件仓库偶发连接抖动**，
     不是"容器没走代理"也不是"代理必然导致失败"。用户提醒"代理在宿主机 12334"后，
     我没有顺着说"对，所以要配代理"，而是拿实测数据把方向纠正回来。
  3. **Docker 镜像的 entrypoint 会激活 venv**：`/opt/esp/entrypoint.sh` 做
     `source export.sh` 再 `exec "$@"`。用 `--entrypoint sh` 直接调 `idf.py` 会报
     `No module named 'rich_click'`。要么走默认 entrypoint，要么自己先 source。
  4. **Windows 的 CMake 缓存不能给 Linux 容器复用**：新建 `build-linux-vocat`，
     用 `tar --exclude='./build*'` 把源码复制到容器 overlayfs 再编译——既避开路径/工具链
     不兼容，也避开挂载盘性能坑。Linux 容器 1m52s 跑完，Windows 此前两次僵死。
  5. **别试图禁用组件管理器**：`IDF_COMPONENT_MANAGER=0` + 把 `managed_components`
     塞进 `components/` 会撞两个坑：短名映射丢失（`esp_mmap_assets` 找不到）、
     `esp_lvgl_adapter` 依赖组件管理器注入的 CMake 属性。这条路是死胡同。
  6. **判断"卡住"看进程 CPU + 日志时间戳**：`prepare_components` CPU 0.4%、
     日志 1.5 分钟不动 = 网络挂起，不是编译慢。给 `idf.py` 加 `timeout 2400` 兜底。
  7. **烧录前先备份**：喵伴里是原厂 xiaozhi 2.0.4.4，写入 Muse 固件会覆盖它，
     建议先 `esptool read_flash` 读回 16 MB 存一份。

- **产出(路径)**：
  - 固件 `.verify/out/`：`muse-gadget.bin` (2.1 MB) / `.elf` (21 MB) /
    `bootloader.bin` / `partition-table.bin` / `sdkconfig.vocat` / `sdkconfig.echoear` /

- **教育内容(下一棒直接学会，不必再查)**：
  1. **`_1` / `_2` 后缀是 PCB 版本号，不是麦克风/通道编号**。`config.h` 的
     `AUDIO_I2S_GPIO_DIN_1/2`、`AUDIO_CODEC_PA_PIN_1/2`、`QSPI_PIN_NUM_LCD_RST_1/2` 里，
     `_1` = V1.0、`_2` = V1.2。`esp_vocat.cc:277-282` 把它们装进 6 个可写全局 `gpio_num_t`，
     `ApplyV12Pins()`(:700-707) 在探测到 V1.2 时整体切换。第一眼极易误读成「双麦两路数据线」——
     官方板只有**一根** I2S DIN。
  2. **为什么缓存路径也必须调 `ApplyV12Pins()`**：`GetAudioCodec()`(:1187) 是 lazy `static` 构造，
     在类构造函数之后才读那 6 个全局变量。软复位走缓存分支时若不切换，V1.2 会用 V1.0 的
     DIN=15 / PA=4，音频直接失效。
  3. **为什么 GPIO48 要「先写输出锁存器，再切成输出」**：外部复位后锁存器默认 0；
     若先 `gpio_config()` 配成输出，会瞬间把 V1.2 的 codec 电源轨拉低，首次触摸/电量计读失败并重启
     （官方 issue #1202）。顺序反了就是玄学重启。
  4. **为什么软复位不能重新探测 PCB 版本**：codec 电源轨有残余电荷，GPIO48 拉低时 ES8311 仍会假 ACK，
     被误判成 V1.0 → 电源被切断 → 未供电芯片经 ESD 二极管钳位共享 I2C 总线 → 重启循环。
     所以用 `RTC_NOINIT_ATTR` + magic `0x31434256` 缓存，只在真正的上电复位时探测。
  5. **I2C 地址有两套表示**：`i2c_master_probe()` 用 7-bit（ES8311 0x18 / ES7210 0x40 /
     CST816S 0x15 / 电量计 0x55），`audio_codec_i2c_cfg_t.addr` 用 8-bit（0x30 / 0x80，
     即左移一位）。写错地址表现为「probe 成功但 codec 初始化失败」。
  6. **`muse_board_t.codec_power` 正好对应 CORDEC_POWER_CTRL**：框架已预留 codec 供电开关回调，
     但本板的 GPIO48 同时是版本探测脚，反复断电会丢 codec 寄存器，所以首次适配建议留 NULL 常供电，
     别机械绑定（方案文档 5.3）。
  7. **框架的板级边界**：一个板文件只填 `muse_board_t` + `muse_board_get()`，
     UI/语音/网络全在共享层；CMake 的 `elseif` 链保证同一时刻只链接一个板文件，
     所以所有板都能导出同名 `muse_board_get()` 而不冲突。新增板要改的是
     Kconfig / CMakeLists / idf_component.yml / overlay / 板文件 / 工具脚本 / 文档，
     **不是**重写业务。`idf_component.yml` 的 rules 只能用 `MUSE_BOARD_ID`。
